# Generic MCP business context: owner-test diagnosis

The October 10 Windows screenshots demonstrate three application defects: automatic overview stopped on the first empty result, source configuration exposed nested simple parameters as JSON, and Save did not prevent incomplete source settings. The dropdown also mixed ready sources with sources requiring configuration. Business-source ranking previously gave status and administrative operations too much priority. These issues are corrected generically, without vendor mappings or an AI provider.

Enabled means permission to use an authorized tool; ready additionally means its arguments validate. Required account, folder, project, or other business identifiers must come from the real account. Enabling every tool cannot supply these values. Required object containers may be initialized only when an empty object validates; identifiers, schema defaults, examples, and enum values are never invented.

Automatic mode checks up to three ready, authorized sources. It continues after empty results, status-only responses, or tool failures, and reports each outcome. Explicit selection checks only that source. The pane distinguishes missing settings, disabled verified reads, empty results, status metadata, rejected arguments, tool failures, and the automatic limit. Refresh retries; Configure pane supplies real values; Tools provides direct navigation to review permissions.

Simple nested scalar parameters use labeled fields and validation before Save. Browser validation avoids dynamic code generation so it works under the existing Content Security Policy; the desktop runtime retains full JSON Schema validation. Arrays, maps and conditional schemas remain advanced JSON. Optional discovery requires explicit trust and a user click. A ready verified read source must declare a collection with the exact parameter field name and matching scalar type. Generic `id` fields are not guessed to be account or folder IDs. Results are bounded, validated, never selected automatically, and checked again for revoked permissions, binding changes and endpoint changes. Sources without suitable output schemas require values from the business app.

The screenshots alone do not establish why the tested Zoho source returned no records, whether its account contains matching records, which permissions the server requires, or which identifier values are correct. Those questions require sanitized runtime outcomes and MCP input/output schemas. Copy sanitized overview diagnostics records only source positions, outcome codes and counts, excluding argument values, endpoints, credentials and record content. Discovery details provide schema shapes separately. Status-only success does not establish that a business collection is empty.

Security remains enforced at execution: name-based ranking never authorizes a capability; untrusted, mutating, disabled and malformed sources cannot gain access through configuration or choice discovery. Demo account isolation and the production credential model are unchanged.

## Automatic business workflows

Automatic overview now resolves required scalar identifiers through authorized read-only discovery dependencies, to a maximum of three dependency levels, six discovery calls and three record reads within the existing 20-second deadline. Discovery is shared within a refresh. Candidates must declare a collection containing the exact identifier name and matching scalar type; all complete arguments and declared tool responses undergo runtime schema validation. Cycles, missing schemas, truncated discovery, untrusted/mutating tools, permission changes and missing identifiers cannot produce guessed arguments. Catalog-only grants remain restricted to their reviewed argument set. Explicit descriptions saying an operation marks records read veto a read-looking name and positive read annotation; descriptions never grant authority.

A single valid discovered account/location value can be used automatically. Multiple values become labeled business choices in the pane. Remembered choices are stored with the existing encrypted connection configuration, scoped to discovery binding and field type, reset when the endpoint changes and checked against freshly returned values. A disappeared choice cannot be reused. Manual source configurations continue to take precedence. Selecting a record source may discover its dependencies, but does not read another record source.

For mail sources declaring folder inputs, actual returned folder names matching Inbox and Sent produce separate views, each showing at most five records. Unknown or localized folder names require a choice; a lone Inbox is never reused as Sent. Unsupported Sent discovery receives recovery guidance. Inventory overviews show at most five returned products; this does not claim best-selling products or chronological ordering without corresponding data. Generic rendering remains available for other app capabilities. With no saved app selection, connected mail capabilities are preferred on the left and another business app on the right; saved selections and Demo placement are retained.

No AI provider is needed for these supported workflows. Existing Ask G-Bot remains available when a provider is configured. This change does not add autonomous model-generated workflows: connecting a model does not turn undocumented identifier relationships into trusted contracts or create permission. Tool descriptions supplied for Zoho helped identify useful capability patterns, but they contain neither actual input/output schemas nor account response data. Live Zoho compatibility still requires owner testing against those contracts. Providers using generic `id` fields without a declared matching identifier, complex searches or undocumented output shapes still require explicit setup. Sanitize runtime schema/outcome diagnostics before sharing; the actual mailbox records and identifiers should stay private.
